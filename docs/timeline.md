# Incident timeline

The timeline is the append-only record of a session. It has two jobs:

1. **Record** what happened (sensor observations, consent, check-ins,
   alerts, escalation, simulated emergency contact, every word on the
   call) so an incident can be reconstructed and analysed later.
2. **Brief the voice agent** during an incident, through a consent-filtered
   view built from it. The agent has no other source of facts.

It records and serves. It does not detect, schedule or notify: those
components call `timeline.append()` to log what they did.

```
 phone / wearable
   │  raw samples (50 Hz accel, GNSS fixes)
   ▼
 RawRecorder ──► raw JSONL (every sample)      src/sensors/raw-recording.ts
   │  batch
   ▼
 accelerometerFeatures()                        src/sensors/features.ts
   │  window features + raw_ref
   ▼
 Timeline.append() ──► timeline JSONL           src/timeline/timeline.ts
   │  (validated, consent-checked, hash-chained)
   ▼
 buildOperatorBriefing() ──► briefing JSON + evidence JSONL ──► voice agent
```

Examples, regenerated by `npm run examples` and checked by tests:

| File | What it shows |
| --- | --- |
| [`no-response-incident.jsonl`](./examples/no-response-incident.jsonl) | 42-event timeline: setup → calibration → stillness → missed check-in → host → backup → simulated emergency → call. |
| [`no-response-briefing.json`](./examples/no-response-briefing.json) | The briefing the agent receives at the moment the operator answers. |
| `data/examples/synthetic-raw-accelerometer.jsonl` | The raw batches behind every motion window (~9 MB, git-ignored; created by `npm run examples`). |

## Two stores

**Why not put every sample in the timeline?** At 50 Hz that is ~180,000
rows per person per hour. The events a responder needs would be buried,
and CLAUDE.md requires raw recordings to be kept apart from derived
features. So:

| Store | Holds | Read by |
| --- | --- | --- |
| Raw recording | Every sample, in batches | Later analysis, re-computing features, improving the detector |
| Timeline | One `sensor.motion_window` per window (features) + every other event | Incident Card, briefing, audit |

Each window's `provenance.raw_ref` (`rec_0001#11`) names the exact raw batch
it came from. A test recomputes every window from its batch, so a feature
can always be traced back to and verified against its samples.

### Raw batch (one JSONL line, abridged)

```json
{"schema_version":"1.0","recording_id":"rec_0001","batch_seq":11,"session_id":"ses_0001","participant_id":"par_0002",
 "stream":"accelerometer","sample_rate_hz":10,"started_at":"2026-10-17T23:51:00.000Z",
 "channels":[{"name":"x","unit":"m/s^2"},{"name":"y","unit":"m/s^2"},{"name":"z","unit":"m/s^2"}],
 "device_kind":"synthetic","data_origin":"synthetic_scenario",
 "samples":[[0,0.232,0.298,9.791],[100,0.24,0.29,9.781], …]}
```

Rows are `[offset_ms, x, y, z]`; `channels` describes the columns once, so
rows stay small. Units are fixed per stream. The `location` stream uses
`[offset_ms, latitude, longitude, accuracy, speed, heading]`.

**Velocity** comes from location fixes (GNSS speed and heading), not from
the accelerometer: integrating acceleration drifts within seconds.

## Timeline line format

One JSON object per line, fields always in this order. Readers can stop at
`summary`; everything after it is structured detail.

```json
{"schema_version":"1.0","seq":22,"event_id":"evt_0022",
 "occurred_at":"2026-10-17T23:52:00.000Z","recorded_at":"2026-10-17T23:52:00.000Z",
 "type":"sensor.motion_window","category":"sensor",
 "session_id":"ses_0001","incident_id":null,"participant_id":"par_0002",
 "summary":"Motion window for participant par_0002 2026-10-17T23:51:00.000Z–2026-10-17T23:52:00.000Z: movement 0.01 ± 0.006 m/s^2, peak 0.021 m/s^2, still 100% of the window; 600/600 samples (100% coverage).",
 "actor":{"kind":"detector","id":null},
 "provenance":{"component":"sensor_adapter","data_origin":"synthetic_scenario","simulated":false,
               "scenario_id":"no-response-v2","raw_ref":"rec_0001#11","producer":"accel-features@0.1.0"},
 "caused_by":[],
 "data":{"window_start":"2026-10-17T23:51:00.000Z","window_end":"2026-10-17T23:52:00.000Z",
         "sample_count":600,"expected_sample_count":600,"coverage_ratio":1,
         "dynamic_mean_m_s2":0.01,"dynamic_std_m_s2":0.0058,"dynamic_peak_m_s2":0.0211,
         "stillness_ratio":1,"still_threshold_m_s2":0.15,"gravity_vector_m_s2":[0.2508,0.3002,9.7988]},
 "prev_hash":"sha256:d0ee…","hash":"sha256:1b14…"}
```

| Field | Why it exists |
| --- | --- |
| `seq`, `event_id` | Gap-free order; stable IDs other events and the agent can cite. |
| `occurred_at` / `recorded_at` | When it happened vs. when it was logged. They differ for late or buffered device data. |
| `type`, `category` | What kind of event; `category` lets readers filter quickly (all `sensor`, all `notification`). |
| `session_id`, `incident_id`, `participant_id` | Scope. `participant_id` is who the event is *about*, not who caused it. |
| `summary` | A deterministic sentence rendered from `data`, so it can never say more than the data. |
| `actor` | Who or what caused it. Needed to enforce "only the participant can consent". |
| `provenance` | Which component, live/recorded/synthetic, simulated or real, raw source, producer version. Keeps synthetic and recorded data apart. |
| `caused_by` | The causal chain (window → anomaly → check-in → missed → incident). Explains *why* something happened. |
| `data` | Type-specific payload. Units are in field names (`_m_s2`, `_ms`, `_m`) or an explicit `unit`. |
| `prev_hash`, `hash` | sha256 chain. An edited, removed or reordered line fails verification on load. Tamper-evident, not signed. |

## Every event type

Sensitivity `location`/`profile`: the payload reaches responders only under
the participant's `location.responders`/`profile.responders` consent.
"Needs" means the event is refused unless the participant currently holds
that consent.

### Session

| Type | Why it exists | Key fields |
| --- | --- | --- |
| `session.created` | Records the escalation policy in force, so later timing can be checked against it. | `expires_at`, `checkin_response_window_ms`, `escalation_steps[]`, `thresholds_validated: false` |
| `session.participant_joined` | Who was in the session and how they joined. | `role`, `joined_via` |
| `session.participant_left` | Leaving withdraws all consent; later sensor data is refused. | `reason` |
| `session.expired` | Sessions end automatically; marks the end of monitoring. | `expires_at` |
| `session.ended` | Ended early by the host or because everyone left. | `reason` |

### Consent and user-provided data

| Type | Why it exists | Key fields |
| --- | --- | --- |
| `consent.granted` | Only the participant can grant, for themselves. Gates recording and disclosure. | `scopes[]`, `consent_text_version` |
| `consent.revoked` | Stops recording under that scope and withdraws earlier data from briefings. | `scopes[]` |
| `profile.shared` | Self-reported details a responder might need. Sensitivity `profile`. | `display_name`, `pronouns`, `preferred_language`, `emergency_notes` |

### Location

| Type | Why it exists | Key fields |
| --- | --- | --- |
| `location.reported` | Where the device was, and whether it was moving. Always last-known. Sensitivity `location`. Needs `location.group` or `location.responders`. | `latitude`, `longitude`, `accuracy_m`, `fix_at`, `speed_m_s`, `heading_deg`, `altitude_m`, `place_label` |

### Sensors

All need `monitoring`.

| Type | Why it exists | Key fields |
| --- | --- | --- |
| `sensor.stream_started` | Records the sensor and every threshold once, so each window and detection can be interpreted later without repeating them. | `sensor`, `gravity_included`, `device_model`, `sensor_range_m_s2`, `window_ms`, `features{…}`, `detector{…}` |
| `sensor.motion_window` | Continuous movement record, so activity before and after an incident can be reconstructed. | see below |
| `sensor.motion_pattern_observed` | A sequence across windows (impact → stillness, abrupt stop, orientation change, prolonged stillness). Can trigger a check-in. | `pattern`, `observed_from/to`, `impact_*`, `still_duration_ms`, `preceding_activity`, `tilt_change_deg` |
| `sensor.baseline_calibrated` | What is normal *for this person*. Anomalies are measured against it. `caused_by` lists the windows used. | `features[] {name, unit, mean, std_dev, window_count}`, `window_ms`, `sampling_rate_hz` |
| `sensor.motion_anomaly_observed` | A window outside the baseline. Starts the private check-in. An observation, not a diagnosis. | `feature`, `observed_value`, `baseline_mean`, `baseline_std_dev`, `z_score`, `rule {id, comparator, threshold, threshold_validated: false}` |
| `sensor.stream_interrupted` | Data stopped arriving. Separates "no movement" from "no data". | `last_sample_at`, `reason` |
| `sensor.stream_resumed` | Data came back; the gap length bounds what is unknown. | `gap_ms` |

`sensor.motion_window` fields:

| Field | Question it answers |
| --- | --- |
| `dynamic_mean_m_s2` | How much was the person moving? (`\|a\|` minus gravity, so independent of how the phone is held) |
| `dynamic_std_m_s2` | Rhythmic activity (walking, dancing) or a steady state? |
| `dynamic_peak_m_s2` | Was there a sharp jolt, such as a drop or impact? |
| `stillness_ratio`, `still_threshold_m_s2` | How much of the window was motionless, and by what threshold (unvalidated)? |
| `gravity_vector_m_s2` | Which way was the device facing? In the example it flips from upright-in-pocket to flat. |
| `sample_count`, `expected_sample_count`, `coverage_ratio` | Is low movement real, or did samples go missing? |

### Connectivity

| Type | Why it exists | Key fields |
| --- | --- | --- |
| `connectivity.device_offline` | The phone stopped reaching the server. Timers keep running; this is never a reason to cancel. | `last_seen_at`, `detected_by`, `heartbeat_interval_ms` |
| `connectivity.device_online` | It came back; how long it was gone. | `offline_duration_ms` |

### Check-ins

| Type | Why it exists | Key fields |
| --- | --- | --- |
| `checkin.prompted` | The private "are you OK?" sent before anyone else is told. | `checkin_id`, `trigger`, `delivery`, `response_deadline_at` |
| `checkin.responded` | The answer. `duress` looks like a cancel to onlookers but silently asks for help. | `response` (`confirmed_ok` / `requested_help` / `duress`), `method`, `latency_ms` |
| `checkin.missed` | No answer by the deadline: the usual incident trigger. | `checkin_id`, `response_deadline_at` |

### Incidents

| Type | Why it exists | Key fields |
| --- | --- | --- |
| `incident.opened` | Starts escalation; names the triggering event. | `trigger`, `trigger_event_id` |
| `incident.acknowledged` | A responder has the alert. Stops escalation. Does **not** mean the person is safe. | `acknowledged_by_role`, `acknowledged_by_id`, `notification_id` |
| `incident.resolved` | Closed. A separate action from acknowledgment. | `resolution`, `resolved_by_role`, `resolved_by_id` |

### Notifications (simulated transport)

| Type | Why it exists | Key fields |
| --- | --- | --- |
| `notification.sent` | Who was told what, and when. `delivered_fact_event_ids` is exactly what the recipient received; recipients may act only on that. | `notification_id`, `recipient_id`, `recipient_role`, `channel`, `escalation_step`, `attempt`, `is_repeat`, `delivered_fact_event_ids[]` |
| `notification.delivered` | It reached the device. | `notification_id`, `recipient_id` |
| `notification.viewed` | Opened but not acknowledged. Tells the operator someone saw it and did not act. | `notification_id`, `recipient_id` |
| `notification.delivery_failed` | It did not arrive. The escalation deadline still applies. | `reason`, `will_retry` |

### Escalation

| Type | Why it exists | Key fields |
| --- | --- | --- |
| `escalation.step_scheduled` | The registered deadline. `deadline_basis_event_id` anchors it, so repeat alerts cannot push it back. | `escalation_id`, `step`, `target_role`, `due_at`, `deadline_basis_event_id` |
| `escalation.step_fired` | The deadline passed unacknowledged; lateness is recorded. | `step`, `target_role`, `scheduled_due_at`, `fired_late_ms` |
| `escalation.step_cancelled` | Stopped by acknowledgment, resolution or session end. | `step`, `reason` |

### Simulated emergency services and voice

All must be `simulated: true`; the only allowed endpoint is `mock-operator-local`.

| Type | Why it exists | Key fields |
| --- | --- | --- |
| `emergency.simulated_dispatch_requested` | Final escalation step, simulated. Lists what was sent. | `mock_endpoint_id`, `escalation_id`, `delivered_fact_event_ids[]` |
| `voice.call_started` | The mock call began. | `call_id`, `mock_endpoint_id` |
| `voice.utterance` | Every turn, both directions. Agent turns must cite `grounding_event_ids`. | `turn_index`, `speaker`, `text`, `grounding_event_ids[]`, `interrupted` |
| `voice.silence_detected` | Silence on the line; the agent must handle it rather than fill it. | `call_id`, `duration_ms` |
| `voice.agent_error` | The agent failed mid-call. | `error_code`, `recoverable` |
| `voice.call_ended` | How and when the call ended. | `reason`, `duration_ms` |

## Enforced on append

- Payload matches its schema; unknown types or fields are refused.
- **Consent at record time:** sensor events need `monitoring`, location needs a location scope. Data nobody agreed to is never written.
- Consent and profile events are performed by the participant themselves.
- Incident events need an opened incident; `caused_by` points only backwards.
- Emergency and voice events are simulated and target only the mock endpoint.
- `occurred_at` is not in the future (2 s skew allowed); `recorded_at` never goes backwards.
- Sinks are written before the event is committed; a failing sink refuses the append.

## The briefing (what the agent gets)

`buildOperatorBriefing(events, { incidentId, now })` returns **derived state**
that cannot be read off any single line, each part citing a `source_event_id`:

| Section | Why the agent needs it |
| --- | --- |
| `incident` | Open, acknowledged or resolved, and by whom. |
| `person` | Consented self-reported details, or `not_consented` / `not_provided`. |
| `location` | Last fix with speed, heading and `age_ms`; `is_current` is always `false`. |
| `motion` | Baseline, the observation that triggered the check-in, and the latest window with its age. |
| `device` | Online or offline, since when. |
| `escalation`, `alerts` | Who has been alerted, how often, delivered, viewed, failed, acknowledged. |
| `unknowns` | What the agent must say it does not know (condition, current location, stale motion data, …). |
| `evidence.event_ids` / `redacted` | Which timeline lines it may read; which were withheld and why (no content). |

The evidence itself is the timeline lines, not a copy:
`evidenceToJsonl(events, briefing)`. Scope is this incident plus the
participant's own events plus `session.created`; other participants never
appear. Motion windows older than `motionLookbackMs` (default 10 min) are
trimmed from the evidence, except the newest, which shows when data
stopped. Consent is applied as of `now`. `AGENT_DISCLAIMERS` holds the
fixed rules for the agent's system prompt.

## Adding an event type

1. Add an entry to `EVENT_CATALOG` in `src/timeline/schema/catalog.ts`: payload, scopes, sensitivity, `requiresConsent`, `summarize`.
2. Add it to the table above (a test fails if any type is undocumented).
3. Removing or renaming fields is breaking: bump `SCHEMA_VERSION`.
